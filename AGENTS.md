## Architecture

- **.NET MAUI Android-only** app (`net11.0-android`; `SupportedOSPlatformVersion` 31.0). App ID: `com.RainbowSprinkles.AniSprinkles`.
- **Two sibling projects under `src/`** (#62):
  - `src/AniSprinkles.Core/` (plain `net11.0`) — `Models/`, `Utilities/`, non-platform `Services/`, `Services/Abstractions/`, `Converters/`, `Icons/`, and **all** `PageModels/`. The plain TFM is the point: it is what lets `tests/AniSprinkles.UnitTests/` project-reference the page models instead of link-compiling source files.
  - `src/AniSprinkles/` (`net11.0-android`) — everything needing MAUI UI, Android, or the icon font: `Pages/`, `Views/`, `Behaviors/`, `Platforms/`, `MauiProgram.cs`, `AuthService`, `AiringNotificationService`, the CI stubs, the Android fault-injection receiver, and the `Services/Maui/` adapters implementing Core's abstractions.

  Keep them siblings. Nesting one project inside another's directory makes the outer project's default globs sweep up the inner project's sources *and* its `obj/` generated assembly attributes, which fails the build in a way that reads as a code error.
- **Core references neither `CommunityToolkit.Maui` nor `IconFont.Maui.FluentIcons`**, deliberately. Popups, snackbars and toasts go through `IDialogService` / `IUserFeedback`; leaving the package out is what stops that seam eroding. Icon glyphs are mirrored into `Core/Icons/Glyphs.cs` (generated by `tools/generate-glyphs.cs`, validated against the real package by `IconGlyphReferenceTests`) because the package ships platform TFMs only.
- **MVVM** via CommunityToolkit.Mvvm: PageModels extend `ObservableObject`, use `[ObservableProperty]`, `[RelayCommand]`, `[NotifyPropertyChangedFor]`. The four details page models extend `DetailsPageModelBase<TEntity>` instead, which supplies the shared load/error/retry/favourite/external-link spine — see `/project-architecture`. Shell bottom-tab navigation (`library` with `anime`/`manga` sub-tabs, `discover`, `search`, `feed`, `settings`) with programmatic `media-details`, `staff-details`, `character-details`, `studio-details`, and `media-browse` routes. PageModels navigate through the injected `INavigationService` (routes + lightweight query params — never full objects); persist state via the injected `IPreferences`; marshal pool-thread continuations back to the UI via the injected `IDispatcher`; read app metadata via the injected `IAppInfo`. View-facing UX calls go through Core abstractions too — `IDialogService` for confirmations, prompts and the bottom-sheet pickers, `IUserFeedback` for snackbars and toasts, `IExternalBrowser` for "view on AniList" — each implemented in `src/AniSprinkles/Services/Maui/`. A PageModel must not reach `Shell.Current`, a popup type, or an Essentials static directly: `Shell.Current` and `Application.Current` return **null** off-device rather than throwing, so such a call silently no-ops and its test passes without exercising anything. The one exception is `HapticFeedback.Default.Perform` in `EntryActionCoordinator` — it returns nothing, has no observable effect to assert, and is already wrapped in a swallowing `catch`, so a seam would buy nothing.
- **DI**: Services and tab PageModels (`AnimeLibraryPageModel` and `MangaLibraryPageModel` — two singletons over one parameterized `MediaListPageModel`, #12 — plus `DiscoverPageModel`, `SearchPageModel`, `SettingsPageModel`) are singleton. All Pages and details PageModels (`MediaDetailsPageModel`, `StaffDetailsPageModel`, `CharacterDetailsPageModel`, `StudioDetailsPageModel`, `MediaBrowsePageModel`) are transient. See `/project-architecture` for the full DI table and page patterns.
- **Services**: `AuthService` (OAuth + SecureStorage), `AniListClient` (GraphQL + viewer ID cache), `ErrorReportService` (Sentry + `ILogger`), `SensitiveText` / `SentryScrubber` (bearer-token redaction), `SentryCrashSeverity` (crashes sent as `fatal`, #180), `SentryLogNoise` (log entries kept out of Sentry, #230), `FileLoggerProvider` (rotating async file log, Debug = 1 MB × 3 / Release = 256 KB × 3), `AndroidLogcatLoggerProvider` (bridges `ILogger` → `adb logcat` on Android), `LoggingHandler` (HTTP DelegatingHandler), `AiringNotificationService` (WorkManager periodic check), `DiagnosticsLogBuffer` / `DiagnosticsSessionLog` / `DiagnosticsSessionFlusher` / `DiagnosticsReportBuilder` / `SentryDiagnosticsSink` + `DiagnosticsReportCoordinator` (user-sent diagnostic reports, #112). See `/airing-notifications` for the notification subsystem.
- **Global usings** (`GlobalUsings.cs`): `Models`, `PageModels`, `Pages`, `Services`, `IconFont.Maui.FluentIcons`. `Converters` and `Utilities` require explicit `using`.
- **Key NuGet packages**: `Microsoft.Maui.Controls`, `CommunityToolkit.Mvvm`, `CommunityToolkit.Maui`, `Sentry.Maui`, `Syncfusion.Maui.Toolkit`, `IconFont.Maui.FluentIcons`.

## Integration Points (AniList API)

- **Endpoint**: `https://graphql.anilist.co`. Auth: OAuth implicit grant, redirect URI `anisprinkles://auth`, token in `SecureStorage` keys `anilist_access_token` and `anilist_access_token_expires_at`.
- **Every request must carry a `Referer: https://anilist.co/` header** (#160). AniList rejects any request that has neither a `Referer` nor an `Authorization` header with HTTP 403 — and the body says *"The AniList API has been temporarily disabled due to severe stability issues"*, which `AniListErrorClassifier` reads as an outage marker. So the failure does not present as "we sent a bad request", it presents as a false **"AniList is Down"** banner while AniList is serving other clients normally. A token satisfies the same filter, but cannot be the whole answer: signed-out browsing (Discover, Search, every details page) has no token by definition, and `AiringScheduleFetcher` has none by design. The header is set in **two** places — `AniListClient.SendAsyncCore` and `AiringScheduleFetcher.Fetch` — because the worker deliberately bypasses the client; if a third path to AniList is ever added, it needs its own. `AniListRateLimitHandler` rebuilds requests from a `RequestTemplate` on retry and copies request headers across, so retries keep it; there is a test pinning that.
- **Signed-in API behaviour can be tested from the desktop, as the test account.** `driver.ps1 dump-token` (#160) writes the dedicated test account's token to `tmp/dev-token.txt`. That file is git-ignored, so it lives in the **main checkout only**: a worktree has to read it from there, at `$(git rev-parse --git-common-dir)/../tmp/dev-token.txt`. The recorder reads the same file. Send the token as a `Bearer` header for read-only probes of how AniList answers a signed-in viewer, where that can differ from signed-out. #199 is the example: for a viewer with Display Adult Content off, AniList filters top-level reads (`Page.media` returns no 18+ titles even when asked for `isAdult: true`, and `Media(id:)` of one returns `404 "Not Found."`), but not nested connections, which return them exactly as signed out. Never print it, log it, or put it in a command line. To find out what the account's settings are, query `Viewer { options { ... } }` rather than assuming.
  - **The test account is `AniSprinkles` (id 7720462)**, not the user's personal account. A session signed in as it should say so rather than treat its list as the user's.
  - **The account is shared.** The user, other sessions and the recorder all use it at the same time, often on another emulator, so its list, favourites and settings can change between two of your requests. Don't read an unexpected change as a bug in your own work until you've ruled that out.
  - **Writing to it is allowed without asking.** It is a throwaway test account, not the user's own, so list saves, settings changes, favourites, recording fixtures with `tools/record-anilist-fixtures.cs` and seeding with `tools/clone-anilist-list.cs` all need no sign-off. Two limits: add nothing unsavoury (no hentai, Ecchi or other 18+ titles — the account's content ends up in public fixtures and screenshots), and leave its settings as you found them when a change was only for a test, since other runs read them. The same token is usually in `ANILIST_RECORDER_TOKEN` as well.
- **Viewer ID caching**: lightweight `Viewer { id }` query cached by token string; invalidates on re-auth.
- **Person names come from `userPreferred`, never `full`** (#130). AniList resolves `userPreferred` server-side against the viewer's Staff Name Language, and it is script-aware where `full` is not: measured on a real account set to `ROMAJI`, `full` returned "Bairstow Caitlyn" for a Latin-script name while `userPreferred` returned "Caitlyn Bairstow" (a Japanese name flipped in both). All eleven `name { ... }` selections request it, and `StaffNameFormat` falls back to `full` only when it is absent. The cost is that a change needs a refetch rather than a re-projection — see `InvalidateEntityCache` under Caching.
- **Operations**: `Viewer`, `ViewerFull`, `MediaListCollection`, `Media`, `SaveMediaListEntry`, `DeleteMediaListEntry`, `UpdateUser`, `AiringSchedule` / `Staff` / `Character` / `Studio` / `Search` / `DiscoverSections` / `BrowseAnime` (the latter seven work without auth; the browse/search trio sends the token when present so `mediaListEntry` fills in the viewer's list status). `DiscoverSections` batches every Discover row's first page (+ `pageInfo`) into ONE aliased request — keep it that way (rate-limit budget); scrolling a row past its seed pages it through `BrowseAnime`, one request per row-page, via the shared `DiscoverSectionFetch`.
- **`Media(id:)` is type-agnostic, and `type: ANIME` was ours** (#12). Media ids are unique across anime and manga, so the `type` argument is only a filter — `Media(id: 30002)` resolves Berserk while `Media(id: 30002, type: ANIME)` returns 404. Dropping that pin from `MediaQuery` and the three per-section paging queries is what made the details page serve both. `Search` now takes `$type` as a variable, and **an absent `type` searches both** — passing `type: null` explicitly returns an empty list, so the All pill relies on `JsonIgnoreCondition.WhenWritingNull` dropping the variable rather than sending a JSON null; **Discover and `BrowseAnime` are still anime-only on purpose** — `MediaSeason`/`seasonYear` don't apply to manga, so the Airing and Upcoming rows have no manga analogue.
- **Manga progress has two counters and one active unit** (#12). AniList keeps `progress` (chapters) and `progressVolumes` as fully independent fields, relates neither to the other nor to status, and has no auto-complete setting — which counter drives the UI is entirely a client decision. `MediaListEntry.UsesVolumeProgress` picks it, matching AniHyou: chapters unless the entry has volume progress *and* no chapter progress. Everything reads `ActiveProgress` / `ActiveProgressTotal` / `ActiveProgressUnit` rather than assuming episodes, and wording comes from `MediaListVocabulary` so "Watching"/"Reading" and "Episodes"/"Chapters"/"Volumes" can't drift between the details page, the status picker and the action menu. The unit is **derived**, so any caller that writes progress and may need to undo it must capture the unit first and revert through `SetProgressFor` — `SetActiveProgress` could otherwise land on the other field.
- **AniList publishes no chapter schedule.** `chapters` and `volumes` are null for *every* RELEASING series (verified across One Piece, Berserk, Dandadan, Sakamoto Days), and there is no `nextAiringEpisode` equivalent to fall back on the way an airing anime has. So an ongoing manga has no cap, no progress bar, no "chapters behind" and no completion prompt — that is the common case, not an edge one.
- **Rate limiting**: `AniListRateLimitHandler` (a `DelegatingHandler`) serializes all requests, reads `X-RateLimit-Remaining`/`X-RateLimit-Reset` for adaptive spacing, and does bounded `Retry-After`-aware retry on 429 (surfacing `ApiErrorKind.RateLimited` when the wait exceeds the cap or retries are exhausted).
- **Transient retry**: `AniListClient.SendAsync` retries once (short delay) on plausibly transient failures — `Network`, `Authentication` (e.g. AniList's sporadic `400 "Invalid token"` on a valid token), and `Unknown` — and **not** `RateLimited` (owned by the handler above), `NotFound`, or `ServiceOutage`. A recovered blip stays a `Warning` breadcrumb and isn't reported to the outage tracker.
- **`NotFound` is no longer a dead end (#158).** It is still excluded from the *automatic* retry above, but the error card now offers Retry and produces a report like every other failure — it used to get neither, and `ErrorStateView` gates Copy/Share on that report string, so the error a user can least explain was the only one they could neither retry nor send. The classifier now matches AniList's `"Not Found."` message **exactly** rather than as a substring anywhere in server text (`AniListErrorClassifier.IsNotFoundMessage`); a substring hit turned any transient failure containing those two words into a permanent, silent dead end. One consequence to know about: `NotFound` now reaches Sentry, deliberately, because the frequency data is what was missing. Fingerprint it down if it proves noisy.
- **Caching**: `CachingAniListClient` decorates `IAniListClient`, caching character/staff/studio reads for the session and coalescing concurrent same-key fetches. `InvalidateEntityCache()` drops them; `SettingsPageModel` calls it when Staff Name Language changes (#130), because names render from `userPreferred` — resolved server-side against that setting, so cached reads hold a stale rendering. Invalidate-only, no refetch: pages reload as the user navigates to them. Other reads (lists, search, media, discover/browse) pass through — broader caching is a planned follow-up. Discover sections have their own ~20-minute TTL cache inside the singleton `DiscoverPageModel` (invalidated by pull-to-refresh, an adult-toggle flip, or an auth change) because the rows carry viewer-relative `mediaListEntry` state.
- **On Android a cancelled request is not an `OperationCanceledException`.** `AndroidMessageHandler` disconnects the underlying `HttpURLConnection`, so the read already in flight fails with `Java.Net.SocketException("Socket closed")` and reaches managed code as a **`System.Net.WebException`** — a type no `catch (OperationCanceledException)` in the app matches. Both HTTP boundaries therefore consult the *token*, not the exception type — but **not the same token**, and the difference is the whole trick:
  - `AniListClient.SendAsyncCore` holds the **caller's** token and calls `ThrowIfCancellationRequested()` before classifying, so a superseded search or a page left mid-load abandons quietly while an uncancelled socket drop still classifies as `Network`.
  - `LoggingHandler` sits *inside* the pipeline, where the only token in scope is HttpClient's **linked** one — cancelled by `HttpClient.Timeout` as well as by the caller. Treating that as cancellation files a 100-second timeout away as a breadcrumb, hiding the exact failure the handler exists to report. So `AniListClient` records its own token on `request.Options` under `LoggingHandler.CallerCancellationToken`, and the handler reads that; with no token recorded it logs `Error`, because a redundant Sentry event is cheaper than a missing one.
  - `AniListRateLimitHandler`'s `RequestTemplate` copies `Options` across when it rebuilds the message (which it does on **every** send, not just retries), or none of the above would reach the handlers below it.

  Left unhandled, a user typing through the search debounce got a "Search failed" snackbar and an error report per keystroke.
- **HttpClient**: singleton; pipeline is `AniListRateLimitHandler` → `LoggingHandler` → `HttpClientHandler`. Bearer token and `Referer` attached per-request in `AniListClient.SendAsyncCore`. The "public query, no auth needed" pattern is gone (#160): operations that do not *require* a token still send one when the app holds one, because withholding a credential we already have buys nothing and costs the only other thing AniList's filter accepts.

- **Toolchain (#168)**: `global.json` sets the SDK floor at `11.0.100` and selects Microsoft.Testing.Platform as the `dotnet test` runner. It is a floor, not a pin: `rollForward` is `latestFeature`, so a build uses the newest installed 11.0 SDK, later feature bands (`11.0.200`, `11.0.300`) included, and CI installs `11.0.x` to match. A new band can therefore bring new analyzer warnings without any change in the repo. Every package version lives in `Directory.Packages.props` (Central Package Management) — a `PackageReference` in a project file names the package and carries **no** `Version`, and adding one is a build error (`NU1008`). `Directory.Build.props` holds what all projects share (`Nullable`, `ImplicitUsings`, runtime async). Both files also reach the file-based tools under `tools/`. Anything that needs a package's version reads it from `Directory.Packages.props` — `IconGlyphReferenceTests` and `tools/generate-glyphs.cs` both do.
- **Android runs on CoreCLR only.** .NET 11 removed Mono from Android: `UseMonoRuntime=true` is `NETSDK1242`, `RunAOTCompilation` is `XA1044`, and `UseInterpreter` is ignored. Release is partial ReadyToRun plus the JIT. Every project compiles with runtime async (`Directory.Build.props`, #178), so async methods that return `Task` or `ValueTask` get no compiler state machine and no `MoveNext` frame in stack traces. `async void` methods and lambdas (event handlers, `OnAppearing` overrides) are not covered and keep both. A crash on a background thread reaches Sentry as **two** events (#180, from `Sentry.Maui` 7.0.0; on 6.12.1 only the second arrived): the managed exception, with its type, message and managed frames, under mechanism `AppDomain.UnhandledException`, and then a native `SIGABRT` under `signalhandler`, from the runtime's `abort()` that follows. Thread, `Timer` and thread-pool callbacks all behave this way (verified on device). The managed one is the event to triage. The `abort` duplicates group into one Sentry issue, ANISPRINKLES-2V, which is deliberately left **unresolved, not ignored**: a genuine native abort (`Environment.FailFast`, a runtime abort, and without uploaded symbols possibly any native `SIGABRT`) can group into the same issue, so ignoring it would hide real crashes. When 2V moves, check for a managed event at the same time before treating it as new. Nor is the duplicate dropped in code: that needs `Native.EnableBeforeSend`, which the SDK marks experimental and lossy for every Android-side event, and only a marker written when a managed crash is recorded could tell the duplicate from a genuine abort. The SDK sends unhandled managed exceptions at level `error`; `SentryCrashSeverity` raises terminal ones to `fatal` in `BeforeSend`, which includes UI-thread exceptions that `MainActivity`'s `UnhandledExceptionRaiser` keeps alive with `Handled = true`, since the SDK counts those as terminal too.
- **R8 runs in Release only, and cannot see .NET's JNI calls.** A Java method that only .NET calls looks unused to R8 and is removed, so it fails at runtime with `NoSuchMethodError` / `IncompatibleClassChangeError` in Release and works in every Debug and CI-stub build. v0.16.0 shipped that way: `UseMaterial3` put Material's `Slider` behind MAUI's `<Slider>`, R8 removed `addOnChangeListener`, and every details page failed to render. Keep rules live in `src/AniSprinkles/Platforms/Android/proguard.cfg`, which keeps all of `com.google.android.material.**` (about +1 MB of uncompressed dex). A new bound Java library, or a MAUI handler drawn by a different native control, may need its own rule.
- **`dotnet test` output is MTP's**, not VSTest's: a `Test run summary: Passed!` line followed by indented `total:` / `failed:` / `succeeded:` / `skipped:` lines. `ci-build-and-preview.yml` parses exactly that to enforce its skipped-test and minimum-total gates, so a runner change has to update the parser with it. `--filter` still takes VSTest syntax (`--filter "FullyQualifiedName~TokenStoreTests"`), which NUnit3TestAdapter translates; `--test-parameter` feeds `TestContext.Parameters`.

- **CI**: `ci-build-and-preview.yml` runs on every PR — build and unit tests, a **Release build that is installed and launched on the emulator** (the `build-release` job plus the "Release launch gate" step; it fails the run unless the signed-out Library page renders "Sign in to AniList", a string the step first checks still exists in `AnimeLibraryPage.xaml`), then the CI-variant screenshots, then the UI journeys against the same emulator (#131, see Build and Test). The Release gate exists because nothing else compiled or started a Release build before a store release did (#155). `android-release.yml` triggers on Release publication (or manual `workflow_dispatch`). `promote-release.yml` promotes between Play Console tracks (internal → alpha → beta → production).
- **CI screenshots live on `ci-screenshots/*` branches, never in a PR or on `main`** (#212). Each run force-pushes its set, quantized with `pngquant` plus a `manifest.txt`, to `ci-screenshots/pr-<N>` as one parentless commit, and the PR comment embeds them by that commit's SHA. When the PR closes, `ci-screenshots-on-close.yml` deletes that branch. On a merge it first promotes the set to `ci-screenshots/main`, but only if the manifest says it is complete and was captured from the merged head: `latest/` (what `README.md` links to) plus `history/<YYYYMMDD-HHMMSS>-pr<N>/` for the newest 10 merges (`HISTORY_KEEP`). That branch is also a single force-pushed commit, so nothing grows. The branches are CI's: don't push to them, merge them or base work on them. The "CI Screenshots Main" ruleset blocks deleting `ci-screenshots/main` (and only that, since promotion needs force pushes). `screenshots/` is gitignored; it is only CI's capture folder. Committing PNGs to PR branches is what this replaced: every merge of `main` conflicted on all 10 binaries, and each merge added ~14 MiB to `main`'s history. `tools/Seed-ScreenshotHistory.ps1` built the first `history/` from those old commits.
- **Version scheme**: `ApplicationDisplayVersion` from release tag semver (`vX.Y.Z` → `X.Y.Z`); `ApplicationVersion` (versionCode) from `YYMMDDNNN` (date + run_number mod 1000). Only `android-release.yml` sets them, so every other build is the csproj's `1.0` / `1`. To tell those builds apart (#207), the `_StampBuildSource` target in `AniSprinkles.csproj` writes `AssemblyMetadata` for the branch, commit, `git describe --tags`, dirty tree and `StoreBuild`. `MauiAppEnvironment.Build` reads them into a `BuildIdentity`, which formats the Settings version label (`v0.15.0+12 · branch @ sha*`, or `v1.2.3 (261117042)` for a store build) and the diagnostics report's `source:` line. The CI build jobs pass the PR head as `-p:SourceBranch` / `-p:SourceCommit`, because their checkout is GitHub's merge commit, and check out with `fetch-depth: 0` so `git describe` has tags. `android-release.yml` passes `-p:StoreBuild=true`.
- **Unit tests** — `tests/AniSprinkles.UnitTests/` (NUnit 5 on Microsoft.Testing.Platform via `NUnit3TestAdapter` with `EnableNUnitRunner`, plus `NUnit.Analyzers`, `net11.0`, NSubstitute). Same framework and versions as KingdomWatch, so the two repos share one (#175). Project-references `src/AniSprinkles.Core/`; there are no link-compile globs any more (#62). Covers pure algorithms, PageModel state machines, and repo-level file validation (`.xaml` well-formedness, icon-glyph resolution). Test doubles live in `Fakes/`. There is no on-device test project yet — #169 tracks adding one.
  - **Watch what throws vs. what returns null off-device.** On the plain `net11.0` TFM, `Shell.Current` and `Application.Current` are `null` (a quiet no-op that reads as a passing test), while `Preferences`, `SecureStorage`, `MainThread`, `AppInfo` and `Browser` throw `NotImplementedInReferenceAssemblyException`. Anything a test needs to reach must be injected — `SecureStorage` behind `ISecureTokenStorage` (#119) is the most recent example.
  - **Fixing a bug starts with a failing test.** Write the test that reproduces the reported behaviour, run it, and watch it fail *for the reason you expect*, before touching the fix. A test written after the fix proves the code passes its own description — it does not prove it would have caught the bug, and a test that never failed is indistinguishable from one asserting the wrong thing. If the bug genuinely cannot be reached from `tests/` (see what throws off-device, above), say so explicitly and verify on device via `/run-app` instead — don't quietly skip the step.
  - `AppSettings.Load/Save/Clear/SyncFromViewer` go through the injectable `AppSettings.Storage` seam (#121), so paths ending in them — a successful `SettingsPageModel.LoadAsync`, for instance — are testable. `TestDataBuilder.ResetAppSettings()` installs a `FakePreferences` and returns it.
  - **The execution model is xunit's, kept on purpose** (`NUnitConfiguration.cs`). `FixtureLifeCycle(InstancePerTestCase)` builds a fresh test-class instance per test, so constructors and fields are per-test setup and `IDisposable` classes clean up after every test; `Parallelizable(ParallelScope.Fixtures)` runs classes in parallel and the tests inside one class in sequence. Write constructors, not `[SetUp]`.
  - Test classes that write to the process-wide `AppSettings` statics must be marked `[NonParallelizable]` so they do not run alongside anything else. That includes `AppSettings.Storage`.
  - **Assertions use the constraint model**, `Assert.That(actual, Is.EqualTo(expected))` — actual first, the reverse of xunit's argument order. `NUnit2007` flags a constant in the actual slot, which is usually that swap. Three traps: `Assert.ThrowsAsync`/`CatchAsync` return a `Task` in NUnit 5 and must be awaited, or the assertion never runs (`NUnit2059`); `Assert.That(someDelegate, Is.Null)` binds to the overload that *invokes* the delegate, so pin the value overload with `Assert.That<Action?>(…)`; and `Does.Contain` on strings compares culture-sensitively, not ordinally.
  - **Full coverage is not the same as tested.** Coverage measures which lines *ran*, not which inputs were *considered*, so a page model or converter can sit at 100% line and branch coverage and still accept values nobody thought about. Write tests against the input space rather than the line count: for each public entry point, ask what a caller can actually pass instead of what the docs say they should. Enums are the classic trap — an enum parameter looks pinned by the type system, but it is an `int` with names and `(MediaKind)999` casts in silently. Sentinels and boundaries want their own cases (zero, negative, `MaxValue`, `null`, the empty collection, the default struct), as does any state where two "is this empty/none/valid?" predicates could disagree with each other. A collection handed out through a read-only interface can still be downcast and mutated unless it is genuinely read-only. `/self-review` carries the full procedure — build the matrix of entry points against input classes, then name the empty cells deliberately.
- **UI journeys** — `tests/AniSprinkles.UITests/` (#131): NUnit tests that run on the host and drive the real app on an emulator through its DevFlow agent (`Microsoft.Maui.DevFlow.Client`), the way dotnet/maui's own UI tests drive theirs through Appium. That is also why NUnit works here when it cannot run *on* a device (#169). They cover what a page-model test cannot see by construction (#227): what every pushed page shows after a tab return (`TabReturnJourneys`), Shell's tab behaviour around pushed pages — #177's strip and #200's re-tap (`NavigationJourneys`) — and list edits followed to where they land, Move to, Up Next and a details-page status change or quick +1 reaching the Library (#225) included (`ListEditJourneys`). A candidate for a new one: behaviour a unit test cannot see (page lifecycle, a change crossing pages, real Shell navigation), not logic `tests/AniSprinkles.UnitTests/` could pin. CI runs them in the UI Screenshots job after the captures, and a failure fails the run; Build & Test skips the project, having no emulator. Locally, `driver.ps1 up`, then the command at the top of Build and Test with the agent port it printed. Waits are 10 s, polled every 250 ms (`AppDriver`).
  - **They only run signed in as the test account.** A journey changes settings and the app saves them to whoever is signed in, so `TestAccountGuard` fails the run unless the Settings profile name is the fixtures' account. A `-p:CiBuild=true` build always is.
  - **Switch tabs with a real touch, never the agent's tap.** DevFlow's tap invokes an element's action directly. On a Shell tab that switches tabs some other way than a finger does, and a pushed page then gets no `OnNavigatedTo` on its tab return — so a journey switching tabs that way passes while the bug it exists to catch is live (verified 2026-11-20 on agent `0.1.0-preview.14.26555.2`, for the agent's `Tab_<route>` markers and the native `BottomNavigationItemView` alike). `App.GoToTabAsync` injects `adb shell input tap` at the item's centre instead, claiming the run's mutation lease first (`claim`) because adb bypasses the agent and would otherwise touch an app another session holds, which is why the suite takes `--test-parameter Device=<serial>` and finds adb through `ANDROID_HOME`, `ANDROID_SDK_ROOT` or the PATH. That is temporary: DevFlow's pointer sessions do real touches, and #228 drops the adb path once a release ships them. Navigating by absolute route (`//library/anime`) does the same damage to the *next* pushed page, so the suite resets by re-selecting the Library tab, as a person does.
  - **Journeys that write list data run only on fixture replay.** `App.RequireFixtureReplayAsync` skips them unless the app is a `-p:CiBuild=true` build, which a Debug build reports through the `uitests_fixture_replay` preference `MauiProgram` writes at every launch. On a live build they would write to the test account, which is also what the fixtures are recorded from, and a completion cannot be undone (AniList keeps its completed date; Up Next adds titles). Replay keeps writes in memory (`MutationState`) until the next launch, and each journey puts back what it moved, so a second run against the same launch starts from the same Library. Titles are looked up by their Romaji text, which `Journey`'s setup resets to.
  - **The agent reports realized views as visible, on screen or not.** A Library card scrolled out of the list, and every card on a tab that is not current, comes back with `IsVisible` true. Judge on screen from bounds (`App.ScrollLibraryToAsync`), and when the same id shows on two tabs (`MediaCardTitle` on the Library and View All), exclude what was there before the navigation. `IsVisible` is the element's own property, not whether anything above it is shown: a chip in a collapsed Settings section keeps `IsVisible` true and its last bounds, so a section's state is read from the element the collapse binds (`<section>Content` in Settings, the header chevron's rotation in the Library), and sections keep their state for the launch, so a journey sets the ones it relies on and puts them back. `Journey`'s setup does that for Watching, clears a Library search filter (which hides titles and turns a count into "1/4") and puts it back in teardown, and its Library reset touches the Anime sub-tab, which re-tapping the bottom tab never changes. The view mode is saved across launches, so a journey that needs the list to scroll opens enough sections to scroll in Compact too.
  - **Proving a journey can fail.** Each new one was run against the bug it guards (#227): the legacy Shell pin removed (#177, the details title drops by the strip's height), `TabReselect`'s scroll-to-top removed, the #221 canary fix reverted, and the staff page's and View All's lifecycle moved from `OnNavigatedTo` to `OnAppearing`. With the pin removed only #177's journey can judge: the tab re-tap hook lives on the legacy renderer, so the rest of the suite needs it moved first (see the Shell pin under Architecture). Removing `ViewModel.RefreshDisplaySettings()` from `MediaDetailsPage.OnNavigatedTo` is not enough to fail the details journey — `_loader.OnAppearing()` there re-projects through the reuse guard too. The regression it catches is #127's: the refresh living in `OnAppearing`, which a tab return never calls.

## CI Stubs (`-p:CiBuild=true`)

Passing `-p:CiBuild=true` in a **Debug** build appends `CI` to `DefineConstants`. This activates `#if CI` blocks that swap in stub services. Do **not** use `-p:CiBuild=true` with `-c Release`; the project file only supports this for Debug builds, and Release builds error out.

- `CIAuthService` (`src/AniSprinkles/Services/CI/`) — always returns `"ci-stub-token"`; app appears authenticated
- `CIAiringNotificationService` (`src/AniSprinkles/Services/CI/`) — all methods are no-ops; `RequestPermissionAsync` returns `true`
- **AniList itself is not stubbed any more (#134).** `CIAniListClient` is gone. `FixtureReplayHandler` sits at the *bottom* of the HTTP pipeline — the slot `FaultInjectingHttpHandler` already occupies — and answers each request from a response recorded against a dedicated test account. Everything above it is the real thing: `AniListClient`, `CachingAniListClient`, `AniListRateLimitHandler`, `AniListErrorClassifier`. That is the point of the change. The old stub implemented `IAniListClient`, so it sat *above* all of that and none of it ran in CI; a deserialization or paging regression could not fail a CI run.
- **Where the pieces live, and why.** Loading fixtures means enumerating embedded resources out of the Android assembly, so `FixtureStore` and `FixtureReplayHandler` stay in `src/AniSprinkles/Services/CI/` under `#if CI`. Everything that merely *transforms* JSON — `AdultCanary`, `AiringTimeRebaser`, `MatureContentFilter`, `MutationState`, and the `GraphQlFixture*` types — lives in `src/AniSprinkles.Core/Services/Fixtures/`, because `tests/` can only reach Core and this is logic that decides whether CI's data is correct. `IFixtureLookup` is the seam between the two halves. Those Core files are guarded on **`#if DEBUG`, not `#if CI`**, and the distinction is load-bearing: `dotnet test` builds Core in ordinary Debug with no `CiBuild`, so a `CI` guard would compile them out of the very build the tests link against. DEBUG keeps them out of Release, which is the guarantee that matters, and matches how fault injection already ships.

### Recording and replaying

- **Fixtures** live in `src/AniSprinkles/Fixtures/AniList/*.json`, embedded as `EmbeddedResource` **only** under `CiBuild=true` — that condition is what keeps ~13 MB of JSON out of every Debug and Release APK. `EmbeddedResource` rather than `MauiAsset` because the handler must *enumerate* what it holds, and `Assembly.GetManifestResourceNames()` does that without a generated index to keep in sync.
- **Re-record** with `dotnet run tools/record-anilist-fixtures.cs` (needs `ANILIST_RECORDER_TOKEN`, or `tmp/dev-token.txt` from `driver.ps1 dump-token`). It is resumable, and an existing fixture is answered from disk rather than re-fetched, so a resume costs only what is missing. `tools/clone-anilist-list.cs` seeds the test account.
- **No real Ecchi or 18+ title is kept.** The fixtures are public and end up in screenshots. AniList does not flag Ecchi adult, so one on the test account's list once went in with its cover. The recorder now looks up the genres and adult flag of every title it records, by id. It skips those on the account's list before recording them, and at the end it removes the rest from every fixture on disk, deleting any fixture about one (`MatureContentFilter`, in Core). A title the lookup does not return is treated as excluded. The CI build's only adult content is made up: `AdultCanary` serves the canary plus a couple of invented 18+ titles, all carrying the `18PLUS CANARY` marker the gate greps for. It also answers their details.
- **Addressing** is `GraphQlFixtureKey` (in Core, shared by the recorder and the player so they cannot drift): the operation name plus a digest of the variables. Clock-derived variables are excluded from the key — `DiscoverSections`' seasons, `AiringSchedule`'s timestamp window, `BrowseAnime`'s season — or a fixture recorded in autumn would stop resolving in winter.
- **A miss is a failure, loudly.** An unrecorded request logs `FIXTURE MISS` and returns a 5xx, and the workflow greps logcat for it and fails the run. This is the heart of #134: the old stub answered anything it did not model with an empty list, so a details-page sort silently emptied its section and no screenshot changed. Adding a sort or a deeper page without re-recording now breaks CI instead of quietly under-testing it.
- **A changed query is also a miss.** Each fixture stores a fingerprint of the query it answered; if the app's query has changed, replay refuses rather than answering a new question with old fields.
- **Airing times are rebased** by the age of the recording (`AiringTimeRebaser`), so countdowns stay live instead of drifting into the past — the same trick the old hand-written `UtcNow.AddHours(3)` fixture used, applied to real data.
- **Mutations are synthesized, not recorded** (`MutationState`) — a recorded mutation would be a recording of a change to a real account. It also *remembers*: a deleted entry stays gone from subsequent list reads, a saved one moves to its new section, and both show on every later read that carries the viewer's entry — the details page, Search, Discover, View All, relations, the people pages — in the shape that query selects, with fields the save left null kept as recorded, since AniList keeps them (#225). A removal made from any of those reads matches its title too. And `UpdateUser` **echoes the request into the viewer**, the way the real mutation returns the updated user. Returning an untouched viewer made every Display Preferences change revert on the next Settings load, so that whole section was unverifiable in CI (found while verifying #130). `DisplayAdultContent` is deliberately excluded — the canary below depends on the viewer reporting the toggle off, and that gate must not be flippable from inside the app.
- **Adult-content canary** (`Core/Services/Fixtures/AdultCanary.cs`) — a synthetic entry titled `18PLUS CANARY - FILTER FAILED`, spliced into replayed responses. It carries no adult content: the title is a marker and it has no cover image. Three parts, deliberately different — the **list** has no `isAdult` argument so the canary always comes back and the client-side filter in `MediaListSectionsMerger` must drop it; the **details pages** (#199) are the same, because AniList returns 18+ titles in every nested media connection (voice roles, production roles, appearances, studio productions, relations, recommendations), signed in or out, and none of those connections takes an `isAdult` argument, so `AdultMediaFilter` must drop them; while **browse/search/Discover** filter server-side so it is served only when the request does *not* pin `isAdult: false`. The details splice targets each connection's shape by operation (`AdultCanary.DetailsSplices`) rather than walking for it, so a new details section needs adding there, and every nested media selection in a query must ask for `isAdult` (`AniListQuerySchemaTests` fails one that does not, since a missing flag reads as not adult). The CI gate sweeps the four details pages it visits top to bottom (`sweep_for_adult_canary`), because their sections sit below the fold and a dump only holds what is on screen. The viewer leaves `DisplayAdultContent` off and nothing in CI turns it on, so every surface must filter it out; `ci-build-and-preview.yml` dumps the UI after each capture and **fails the run** if it renders. That wording is load-bearing: the `ui-screenshots` job was `continue-on-error: true` once, so the canary failed its job while the run still concluded success — a gate that detects everything and blocks nothing. Keep that job blocking; the flaky-capture paths are already `::warning::` and don't need it. Before this the adult filter was never exercised end to end (#118). The workflow also asserts the marker still appears in `AdultCanary.cs` (path pinned in `ci-build-and-preview.yml` — moving the file means updating it), so renaming it cannot leave the gate grepping for a string nothing emits.
- **18+ recordings carry no artwork.** The recorder replaces cover and banner URLs on any `isAdult: true` response with a placeholder ending in `default.jpg`, which `ImageUrl.IsReal` already treats as "no image". Metadata is kept — these fixtures live in a public repo, and nothing should fetch or render 18+ imagery from them.

These stubs and the fixtures are **compiled out entirely** in standard Debug and Release builds.

## Fault Injection (runtime, no rebuild)

Every **Debug** build compiles in fault injection, **disarmed**. It is armed over adb against the
running app, so changing what fails costs a broadcast rather than a ~3 minute rebuild (#125). It
replaced the `-p:ErrorSim=true` flag, which no longer exists.

```powershell
pwsh .claude/skills/run-app/driver.ps1 fault GetStudio NotFound next          # client layer
pwsh .claude/skills/run-app/driver.ps1 fault Studio NotFound next -layer http # same op, wire name
pwsh .claude/skills/run-app/driver.ps1 fault any delay next -delay 4000
pwsh .claude/skills/run-app/driver.ps1 fault clear
```

- **It decorates `IAniListClient` rather than replacing it**, so it *composes with the CI stubs*: a
  real screen loads from the fixtures and then the next call breaks. `ErrorSim` failed every call, so
  the screen whose error state you wanted was unreachable — which is why the details pages' error and
  retry states had never been seen on a device.
- **Deterministic scopes only** — `next`, `always`, `firstn:N`, `everynth:N`. No randomness: a fault
  you cannot re-run is not a fixture.
- **`Delay` is independent of failure.** Latency with no error kind is the only way to open the
  cancellation and interlock windows that #116's defect family lives in.
- **Two seams.** `-layer client` (default) decorates the client and works with CI stubs.
  `-layer http` injects into the `HttpClient` pipeline so `AniListRateLimitHandler`,
  `SendAsync`'s retry-once and `AniListErrorClassifier` all run for real — that one needs a real
  signed-in session and does **not** work with `-p:CiBuild=true`.
- **`op` means a different thing per layer, and a miss is silent.** At `client` it is the
  `IAniListClient` method name (`GetStudio`); at `http` it is the GraphQL `operationName`
  (`Studio`) — that is all the handler can see in the request body. They do not reduce to one
  another: `GetMediaListAsync` is `MediaListCollection` over the wire and `SearchMediaPageAsync`
  is `Search`, so no `Get`/`Load`/`Async` stripping would unify them and none is attempted. A
  targeted http profile that misses logs `FAULT http no match` with the operation it actually saw.
- **A profile fires at one layer only.** Both seams share one `FaultState`; without the layer tag a
  single armed profile would fire twice for one logical call.
- Everything is behind `#if DEBUG`, including the exported `BroadcastReceiver`, so none of it can
  reach a Release build — hence no Release guard target, unlike `-p:CiBuild=true`.

See `DEVELOPER_NOTES.md` for the scenario recipes and `/run-app` for the driver verbs.

## Build Quality

The project must build with **zero warnings**, and warnings are fixed rather than suppressed — `#pragma warning disable`, `#nullable disable` and the null-forgiving `!` all need explicit sign-off from the repo owner before they go in, not a comment justifying them afterwards. Do not introduce new warnings; fix any that appear before committing. CA1822 ("member can be static") is suppressed project-wide in `.editorconfig` — MAUI `{Binding}` requires instance members even when they only read static state, so the analyzer produces false positives.

**"Zero warnings" means every project, and the test project is the one that gets missed.** Building `src/AniSprinkles/AniSprinkles.csproj` does not compile `tests/`, and `dotnet test` output filtered for failures hides warnings entirely — which is how 15 analyzer warnings reached a PR while the app builds were reported clean. Check all five before pushing:

```powershell
dotnet build tests/AniSprinkles.UnitTests/AniSprinkles.UnitTests.csproj -c Debug
dotnet build tests/AniSprinkles.UITests/AniSprinkles.UITests.csproj -c Debug
dotnet build src/AniSprinkles.Core/AniSprinkles.Core.csproj -c Debug
dotnet build src/AniSprinkles/AniSprinkles.csproj -c Debug -f net11.0-android
dotnet build src/AniSprinkles/AniSprinkles.csproj -c Debug -f net11.0-android -p:EmbedAssembliesIntoApk=true -p:CiBuild=true
```

Claude Code sessions have a Stop hook that runs whichever of these the change can affect and blocks on any error or warning (`.claude/hooks/build-on-stop.ps1`; see `CLAUDE.md`). It is a backstop, not a substitute — it builds nothing when the sources are unchanged, and it runs no tests.

**A green local suite is not a green suite.** Test classes writing to the process-wide `AppSettings` statics are `[NonParallelizable]` and run one after another, so failures that depend on *the order they run in* surface on CI and not here — #128's pending-upstream markers leaked between tests exactly that way, passing locally every run. `TestDataBuilder.ResetAppSettings()` goes through `AppSettings.Clear()` so those markers reset; **new process-wide state must be reset there too**, or it poisons whichever test happens to run next.

## Engineering principles

**Write the cleanest, most understandable, maintainable and testable version by default.** Reach for a more complicated or lower-level implementation only when there is a *specific, identified* need — a measured performance problem, a platform constraint — never a suspected future one.

Concretely: two explicit properties beat packing state into one; a plain class beats a hand-rolled store; a straightforward projection beats a clever one; an injected seam beats reaching for a static. When a real constraint does force something awkward, say in a comment what the constraint was, so the next reader can tell whether it still applies — the `HapticFeedback` exception under Architecture and the `ConfigureAwait(true)` markers under Project Conventions are both this.

Two standing exceptions, both documented above rather than inferred: **testability** (logic that must be reachable from `tests/` belongs in Core behind a seam, even when that costs an interface) and the **AniList request budget** (batching Discover's rows into one aliased request is not premature cleverness, it is the rule). And when fixing a bug, the failing test comes first — see Build and Test.

## Project Conventions

- **MAUI-first guidance**: do not mix WPF/Xamarin.Forms/Blazor/React patterns unless explicitly requested. Verify MAUI APIs against official Microsoft docs and current project code before recommending.
- **Android Shell is pinned to the legacy `ShellRenderer` (#177).** MAUI 11 moved Android Shell onto handler classes, and on 11.0.10 those redraw the Library tab's ANIME / MANGA strip over a pushed details page after a bottom-tab round trip — live, so tapping it changes where Back leads. `MauiProgram.cs` registers `TabReselectShellRenderer` (`Platforms/Android/`), a subclass of the legacy `ShellRenderer`, for `Shell` on Android to opt out. The subclass only adds the bottom-tab re-tap hook (#200, `Utilities/TabReselect.cs`); lifting the pin means moving its `OnTabReselected` override to a `ShellItemHandler` subclass, which has a virtual with the same signature. Remove it only once `NavigationJourneys.DetailsPage_HasNoTopTabStrip_AfterATabReturn` passes without it (#227), which replays #177's four steps and checks the details page did not move down. Shell tab badges (#14) may need the handler path — check before starting it. Material 3 does not: #172 compared both paths under `UseMaterial3` and they rendered the same. Reported upstream as dotnet/maui#40303.
- **`ActivityIndicator` is pinned to the classic handler under Material 3 (#172).** `UseMaterial3` swaps in Material's `CircularProgressIndicator`, which animates on the UI thread. It stays frozen while a page is being built, which is when our spinners show. `MauiProgram.cs` registers `Microsoft.Maui.Handlers.ActivityIndicatorHandler`, whose `ProgressBar` animates on the render thread. Reported as dotnet/maui#40315. On the driver's emulator, animations are off, so any spinner looks static there. Turn `animator_duration_scale` back to 1 to judge one.
- **XAML: a C# expression for simple logic, a converter for the rest (#168).** MAUI 11 inflates XAML with a source generator by default and compiles `{...}` C# expressions against `x:DataType` into typed bindings that track changes — no preview flag needed on 11.0.10. Use one where a converter would only negate, compare or null-check: `IsVisible="{!HasBanner}"`, `Opacity="{SearchFilterKey == 'All' ? 1.0 : 0.6}"`, `IsVisible="{!string.IsNullOrWhiteSpace(EpisodesDisplay)}"`. Keep a converter when the logic looks up a resource or is shared (`RainbowAccentConverter`, the `SortField*` colour converters), and in two places expressions do not reach: a binding with `Source={x:Reference …}`, and a `?.` path whose first segment is also a member name on the page model (`Media?.SiteUrl` beside a `SiteUrl` property fails to compile with `CS1061` on a generated `__source`).
- **Every binding is compiled; no `x:DataType="{x:Null}"`, no `BindingContext.` paths (#173).** Either one turns a binding back into reflection: a renamed property becomes a dead button at runtime instead of a build error. A `BindingContext.X` path is the quiet one: `BindingContext` is typed `object`, so the source generator emits a reflection `Binding` with no diagnostic. To reach the page model from inside an item template, bind to it directly: `{Binding X, Source={RelativeSource AncestorType={x:Type pageModels:SomePageModel}}}`. A template or view shared by several page models binds to a small Core interface they all implement (`IBrowseMediaItemActions`, `IAuthActions`). A binding that only feeds a constant to a converter takes `Source='Key', x:DataType=x:String`. XC0023 is no longer suppressed, and `CompiledBindingGuardTests` fails on either shape.
- **`closed` hierarchies and `union` types are for new code, not a refactor (#168).** C# 15 has both. Core models "one of several" with enums throughout and has nothing to convert; reach for them when a new type genuinely is a closed set of shapes.
- **Logging**: `ILogger<T>` injected via DI is the canonical path for all app code. Use structured messages. Bearer tokens are always redacted — with one deliberate, Debug-only exception: MAUI DevFlow (#170) records the `Authorization` header verbatim in its network capture, and its storage tools can read the token out of secure storage, the same exposure as `driver.ps1 dump-token`. Both are reachable from this PC only (the agent and its forward listen on loopback, the broker refuses non-loopback clients, browser origins are refused), and none of it exists in Release.
  - Provider wiring lives in `MauiProgram.cs`. `FileLoggerProvider` runs in both Debug (1 MB × 3 at `LogLevel.Debug`) and Release (256 KB × 3 at `LogLevel.Warning`). `AndroidLogcatLoggerProvider` bridges ILogger output into `adb logcat` on Android in all build configs (`AddDebug()` does not reach logcat on .NET MAUI Android). `AddDebug()` stays Debug-only.
  - Exception: `Platforms/Android/MainActivity.cs` and `Platforms/Android/AiringCheckWorker.cs` call `Android.Util.Log` directly because they run before the MAUI DI container is guaranteed to be built (activity lifecycle callbacks; post-reboot WorkManager). Inline comments document this at the call sites. Do not introduce new direct-`Android.Util.Log` callers elsewhere — use ILogger.
  - On-device log file: `{AppDataDirectory}/logs/anisprinkles.log` (+ `.1`, `.2` archives). Pull via `adb shell run-as com.RainbowSprinkles.AniSprinkles cat files/logs/anisprinkles.log` or use `/device-debug`.
  - **`DiagnosticsLogBuffer` is a third provider, in memory, at `LogLevel.Information` in every config (#112).** It exists because the file log drops `Information` in Release, which is every trace worth sending — no `NAVTRACE`, no `PageState`, no `HTTP`. It keeps roughly the last five minutes, bounded by age *and* entry count, and touches no disk. `DiagnosticsSessionFlusher` writes a snapshot to `{AppDataDirectory}/logs/previous-session.log` from the three global exception handlers and `MainActivity.OnPause`, and clears it again on resume — but only when this process wrote it, since a file left by a process that actually died is the thing worth sending. If you change `DiagnosticsLogBuffer.DefaultRetention`, the popup's "5 minutes" copy is a lie; `DiagnosticsDisclosureTests` fails on purpose when they drift. Neither the ring nor `previous-session.log` is cleared on sign-out — a crash spanning sign-out/sign-in is worth reporting, and this is a single-user install. Revisit before first public release.
- **Telemetry**: Sentry crash reporting only (`SendDefaultPii = false`, `TracesSampleRate = 0.0`, plus a `BeforeSend` redaction pass — `SendDefaultPii` governs IP/username, not message content). Use `ErrorReportService.Record()` for handled exceptions.
  - **The app never reads MAUI's `DeviceDisplay` (#230).** On Android, MAUI 11.0.10's `GetDefaultDisplay()` disposes a Java peer that every caller shares, and Sentry.Maui reads `DeviceDisplay.MainDisplayInfo` while building every event, on whatever thread captured it, under a private lock that only covers its own reads. A read of ours racing a background Error log aborted the process outright: a JNI error, no managed exception. Use `ScreenMetrics` (activity `DisplayMetrics`) instead; `DeviceDisplayGuardTests` fails the build's tests on any `DeviceDisplay` or `IDeviceDisplay` in `src/AniSprinkles/` or `src/AniSprinkles.Core/`. It matches comments too, because telling code from comments takes a lexer, and a guard that guesses wrong lets a read through. So comments there say "MAUI's display API" instead. To keep a log out of Sentry, filter it in `SentryLogNoise` (an `AddLogEntryFilter`): `BeforeSend` runs only after the event processors, so by then the display has already been read.
  - **The Sentry event comes from `Record`'s `LogError`, not its `CaptureException`** — confirmed by the `mechanism: SentryLogger` tag on the events. `MinimumEventLevel` defaults to `Error`, so the `ILogger` integration captures first and gets the real id; the explicit `CaptureException` on the next line is then dropped by `DuplicateEventDetectionEventProcessor` (`DeduplicateMode` defaults to `All ^ InnerException`, which still includes `SameExceptionInstance`) and returns `SentryId.Empty`. Worse, `Hub.CaptureEvent` assigns `scope.LastEventId = id` unguarded, so that empty id **overwrites** the good one — which is why `SentrySdk.LastEventId` is also empty. Don't build anything on either value; correlate on exception text and timestamp. Do not "fix" it by swapping the two lines either: the logger-created event is the richer one (it carries the `Context` tag, the logger name and a readable message), and a bare `CaptureException` event has none of that. Cost this out before touching it — #112 tried twice and removed the feature instead.
- **User prefs**: `AppSettings` (static, `Utilities/`) persists title language, score format, adult content toggle, and section order through the injectable `AppSettings.Storage` seam, which defaults to `Preferences.Default` (#121). `DisplayAdultContent` commits the instant the Settings toggle flips via `SetDisplayAdultContent`, ahead of the debounced AniList save (#118) — every browse surface filters on it and only re-checks when it appears, so a late commit left 18+ results on screen. Paging must be pinned to the value its page 1 was seeded under (`_seededDisplayAdult` in `SearchPageModel`, `DiscoverPageModel` and `MediaBrowsePageModel`; passed into `DiscoverSectionFetch.PageAsync`) rather than re-reading the static per page, or one result set can hold two policies. All four surfaces — Library included — compare it against the value their current data was built with. The details pages do the same (#199): `DetailsPageModelBase.DisplaysAdultContent` is captured when a load starts and passed to `AdultMediaFilter` for every page of every section, and returning to a page after the setting moved rebuilds it instead of taking the same-id short-circuit. It is deliberately tracked apart from `DisplaySettingsSnapshot`, which `RefreshDisplaySettings` re-records before the load runs. Title language and score format commit the same way, via `SetTitleLanguage` / `SetScoreFormat` (#128); before that they reached `AppSettings` only once a save had succeeded. A locally committed change outranks the server's copy until the server reports that same value back — for all three now, not just the adult toggle — so neither a refresh elsewhere in the app nor a return to Settings can sync the pre-change value over it; `SettingsPage.OnDisappearing` flushes any pending save so the server catches up promptly. The settings the Settings page holds on its own (staff name language, restrict-messages, activity merge time, airing notifications, and the per-type notification toggles) carry the same markers there — the per-type ones as a set of unconfirmed types, so a change made on another device still arrives for every type the user did not touch. `AnimeSectionOrder` deliberately has none — there is no control for it, so it can only come from the server.
- **The airing job follows the toggle both ways.** `PopulateFromUser` schedules the WorkManager check when airing notifications land on, and cancels it when they land off. Only the enabling half was wired originally, so turning the setting off anywhere else — the AniList website, another device — left this device still scheduled, and the switch read off while notifications kept arriving. Cancelling an unscheduled job is a no-op, so the else-branch is safe on every load.
- **Pushed detail pages get no lifecycle on a tab return.** `OnAppearing` / `OnDisappearing` fire on tab-*root* pages (Library, Discover, Search, Settings) when you switch tabs, but **not** on a page pushed onto a backgrounded tab's navigation stack — the four detail pages and View All (`AppShell.xaml.cs:23-27`). Verified on device: `MediaDetailsPage.OnAppearing` logged exactly once, at the initial navigation, and tabbing away and back produced nothing. **Use `OnNavigatedTo` instead** — it fires on every tab return, and pairs with `OnNavigatedFrom` on the way out; all five pushed pages call `ViewModel.RefreshDisplaySettings()` from it. Confirmed in the same device run: `OnAppearing` 1, `OnDisappearing` 0, `OnNavigatedTo` 3 across two tab round-trips. No unit test will tell you which to use — the page model behaves correctly when called, and the bug is that nothing calls it, so a test driving the page model directly passes while the feature is dead on device. `TabReturnJourneys` in `tests/AniSprinkles.UITests/` pins this for all five pushed pages, the Character page's sort and scroll, and the Library (#131, #227); a new pushed page that depends on a tab return wants a journey there too.
- **`ConfigureAwait(true)` in page models is deliberate.** It is the default, so it changes nothing at runtime — it states that the continuation writes bound state and must stay on the UI thread. `DetailsPageModelBase`, `PaginatedSection`, `MediaBrowsePageModel`, `ListOperationRunner` and `SettingsPageModel` all mark their data-fetch awaits this way. A `ConfigureAwait(false)` inside `AniListClient` governs continuations *inside that method* and does not propagate to the caller, so a page-model await resumes wherever its caller was — which is the UI thread for every lifecycle and command entry point. Don't add `ConfigureAwait(false)` to a page-model await whose continuation touches an `[ObservableProperty]` or a bound `ObservableCollection`.
- **Failed settings saves**: dirty-tracking is baselined against what the *server* reported, not the resolved local value, so a change that never landed leaves the page dirty and the next flush re-sends it (#128). A successful `UpdateUser` clears the markers for the values it actually carried — compared field by field, since the user can change a setting while a save is in flight, and clearing that one would discard a change the server never saw. A save arriving while another is in flight is coalesced into a second pass rather than dropped, and the failure snackbar goes through `ShowFailureSnackbarAsync` so a `ServiceOutage` offers no Retry.
- **Display settings and already-rendered pages**: title language and score format feed computed properties (`Media.DisplayTitle`, `MediaListEntry.ScoreDisplay`, the details rating control), so a change has to re-render what is already on screen. Each surface snapshots a `DisplaySettingsSnapshot` and re-projects in its appearing path when it moved — **never a refetch**, which would spend an AniList request on a formatting change (#127). `Media` and `RelatedMedia` are plain classes and cannot raise `PropertyChanged`, so the observable containers implement `IDisplayProjection` and re-raise the property carrying them (`Media` / `Node`), which makes MAUI re-resolve the nested binding path. A new carousel item type that shows a media title must implement it, or its cards render stale titles forever with nothing to catch it. Title language also moves the Title **sort order**, since `MediaListSection` sorts by `DisplayTitle`.

See `/project-architecture` for page patterns and performance defaults.

### Calling the GitHub API from a Claude Code cloud session

Cloud sessions (claude.ai/code, the mobile app) reach GitHub through a proxy that
holds the real credentials outside the container. Its restrictions change how
tooling here has to be written, and none of them is configurable — setting
`GH_TOKEN` to a personal token lifts none of them. Ported from KingdomWatch,
which hit each of these first.

**The short version: `gh api repos/{owner}/{repo}/...` is the only GitHub surface
that works everywhere.** Every `gh issue`, `gh pr` and `gh label` subcommand is
GraphQL-backed and returns `403` — reads and writes alike. `gh workflow run`
resolves the default branch over GraphQL too; dispatch with
`gh api -X POST repos/{owner}/{repo}/actions/workflows/{file}/dispatches -f ref=main`.

**GraphQL is refused**, except a pinned set of pull-request operations. Review
threads have no REST equivalent on github.com, so the proxy adds its own routes
(`GET .../pulls/{n}/ccr/review_threads`, `POST .../pulls/{n}/ccr/comments/{id}/resolve`
and `/unresolve`) keyed by comment id. github.com answers those with `404`, so
`Get-ReviewThreads` and `Resolve-ReviewThread` in `tools/GitHubApi.psm1` try the
`ccr/` route and fall back to GraphQL on that `404` — go through them (or
`Resolve-PrThread.ps1`) rather than calling either transport directly.

**`gh --paginate` breaks past the first page.** It follows GitHub's
`Link: rel="next"`, which points at the numeric-id form (`/repositories/{id}/...`),
and the proxy rejects that. It only fails once a collection outgrows one page,
so tooling looks healthy until it suddenly isn't. `Get-Paged` (and
`Get-GhPages.ps1` for the skills) walk `&per_page=100&page=N` by hand and throw
rather than truncate. **Cross-repository endpoints** (`search/issues` and
friends) are refused as well: use a repo-scoped endpoint and filter client-side.

**A skill cannot page in a shell loop.** The command-prefix allow rules match the
first word, so `for … do gh api … done` starts with `for` and gets bounced to the
permission classifier. `Get-GhPages.ps1` starts with `pwsh`, and its `-Format` /
`-Contains` filters stand in for `jq`, which is not installed on the Windows dev
machine.

`tools/` and `.claude/skills/` are clear of all of the above; keep them that way.
A `gh issue`/`gh pr` one-liner from memory is the likely way it creeps back in.

## Working with AI Agents

### Commits and pushes

Do not commit or push unless explicitly asked (e.g. "commit this", "push it"). The exception is when asked to create a PR — that implies doing everything needed: branch, commits, push, and PR creation.

### Self-review

After writing code, run through the review checklist in `.claude/skills/self-review/SKILL.md` (`/self-review`). Fix all issues found before presenting. The review loop is internal — do not surface bugs as a list of things found.

### PR feedback review

When asked to pull PR feedback, use `.claude/skills/pr-feedback/SKILL.md` (`/pr-feedback`).

### Presenting options

When presenting 2+ approaches to the user, say what each direction costs and which you recommend. Do not just pick one and proceed without asking.

If your client supports a popup/question UI (e.g. `AskUserQuestion`, `vscode_askQuestions`), **that popup is what asks**: it carries the choices and collects the answer, while the prose carries the reasoning behind them. Don't also render the alternatives as a menu in the message, and don't compress the tradeoffs into the widget's own option descriptions — those are read at the moment of choosing, with no way to compare them side by side. The test is whether the choice could be answered in the popup without the prose; if the choosing happens in the prose, it has gone too far. Without such a UI, lay the options out in prose with their tradeoffs and ask outright.

### Output style

- No AI attribution or agent branding anywhere in generated project artifacts. This includes branch names, commit messages, PR titles, PR descriptions, issue bodies, comments, release notes, and footers. Avoid labels such as "codex", "Claude", "Copilot", "AI-generated", or similar unless the user explicitly asks for them.
- Be terse. Skip pleasantries and preamble.

## Security

- **OAuth implicit grant** via `WebAuthenticator`; tokens stored in `SecureStorage`, never logged.
- Bearer tokens are redacted **at the source**, not at each sink (#124). `SensitiveText.Redact` is applied in `AniListClient` to every server-derived string that becomes an exception message, so the token never enters the exception and the file log, logcat and Sentry are safe by construction. `SentryScrubber` (wired via `options.SetBeforeSend`) is the backstop for exceptions Sentry captures without going through `ErrorReportService`. Classification runs on the raw text and redaction only on what gets stored, so `AniListErrorClassifier` keeps matching "Invalid token" and the outage markers.
- **`SentryScrubber` does not walk attachments**, so it is *not* the backstop for a user-sent diagnostic report (#112) — that report goes to Sentry as an attachment, by a route `SetBeforeSend` never inspects. `DiagnosticsReportBuilder.Build` runs one `SensitiveText.Redact` pass over the whole finished report, and `SentryDiagnosticsSink` redacts the free-text description separately because it takes a third route again (`SentryFeedback`). If you add a section to that report, it inherits the pass; if you add another *sink*, it does not.
- Sentry: `SendDefaultPii = false`. AniList Client ID (`35674`) is a public app identifier, not a secret.
- Sign-out clears both in-memory token fields and both SecureStorage keys.
- Token expiry is tracked and auto-cleared when expired (`IsExpired()` check on access).
